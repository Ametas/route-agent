# Архитектура Go-агента

Согласовано с владельцем 2026-11-06 (решения — в §6). Основан на шести спецификациях в `spec/`;
ссылки вида «A §8.3» ведут туда.

## 1. Что не меняется (договор с оркестратором)

Оркестратор при переходе не трогается, поэтому снаружи Go-агент неотличим от нынешнего:

- **`proto/agent.proto` — тот же файл**, хеш договора совпадает бит в бит (`21108c0a…ac9f`, A §7.4).
  Тест в Go считает хеш тем же каноническим алгоритмом и сверяет с оркестратором.
- **Версия — та же форма** `vX.Y.Z[-N-gHASH]`: иначе оркестратор сочтёт узел отставшим и будет
  обновлять его раз в 6 часов (A §7.3). Версия вшивается при сборке (`-ldflags`) из `git describe`.
- **mTLS и авторизация:** те же файлы сертификатов, та же проверка CN и закреплённого отпечатка,
  заголовок `x-orchestrator-secret`, та же матрица отказов по 31 методу (A §4.3): где-то gRPC-ошибка
  UNAUTHENTICATED, где-то `success:false` со статусом OK — оркестратор различает.
- **Keepalive:** сервер пингует раз в 10 с, таймаут 20 с; в Go обязательно ослабить защиту от
  частых пингов (`MinTime ≤ 5 с`, `PermitWithoutStream`), иначе оркестратор, пингующий раз в 10 с,
  получит «too many pings» (A §3.1).
- **Строки ответов**, которые оркестратор сравнивает или разбирает: таблицы в каждой спецификации.
  Отдельно — текст ошибки команды в форме Node `Command failed: <cmd>\n<stderr>`: его разбирает
  `failureDigest.ts` (C, D). Вывод `caddy validate` в ответе ConfigureCaddy — целиком: оркестратор
  ищет в нём `proxy_protocol` (B).
- **Телеметрия:** поток раз в 2 с, первый кадр не позже 5 с после подключения, `timestamp` — мс и
  строго растёт, `mesh_tunnel_active_peers == len(live_peer_keys)`, сторожевые строки
  (`not_installed`, `built_not_loaded`, …) — как сейчас (E).
- **Файлы на узле те же:** `/opt/route-agent/.env` (все 33 переменные, те же умолчания, A §2.2),
  сертификаты, юниты, пути конфигов sing-box, Caddy, AWG, тыла, Olcrtc.

## 2. Устройство

```
cmd/route-agent/        main: конфиг, логгер, gRPC-сервер, фоновые циклы, остановка по сигналу
internal/
  agentpb/              код из proto/agent.proto (protoc-gen-go, лежит в репозитории)
  config/               .env + окружение, проверка всех 33 переменных (как zod сейчас)
  server/               gRPC: mTLS, keepalive, авторизация по матрице, регистрация методов
  runner/               внешние команды: без shell, аргументами, таймаут на каждую, текст ошибки в форме Node
  fsx/                  атомарная запись (temp + fsync + rename) с правами, «не изменилось — не пишу»
  systemd/              юниты, override, systemctl (позже — D-Bus)
  telemetry/            кадр телеметрии, кеши, самопочинка AWG
  singbox/ caddy/       ApplyConfig, ConfigureCaddy, горячие пользователи, статистика, соединения
  binaries/             приём потоком, проверка до подмены, setcap, откат, перезапуск
  awg/ mesh/            ConfigureAwg, наблюдение, туннель Mesh, DKMS
  firewall/ shaper/     ManageFirewall, tc-шейпинг, sysctl
  rear/ olcrtc/         тыл sing-box/mihomo, WARP-сторож, Olcrtc и поток его событий
  warnings/ diag/       PullNodeWarnings (journalctl), RunNetworkDiagnostic, GetWarpKeyHealth
  update/               SelfUpdate
```

Правила, которых сейчас нет и из-за которых агент «страдает»:

- **Ни одной команды через shell.** Сейчас ~50 строк вида `` `dkms status -m ${name}` `` (A, D).
  Везде `exec.CommandContext(ctx, bin, args...)`; конвейеры (`| awk`, `| grep`) заменяются разбором
  вывода в Go.
- **Таймаут у каждой команды и у каждого HTTP-запроса** (сейчас нет почти нигде, B, E, F).
- **Тик телеметрии не накладывается** на прошлый (сейчас `setInterval` запускает новый, пока висит
  старый, E).
- **Замок на каждую область:** одно применение конфига sing-box, Caddy, AWG, одна загрузка одного
  бинарника за раз; повтор во время работы ждёт или получает «уже идёт» (сейчас замков нет).
- **Секреты пишутся 0600 и атомарно** (сейчас ключи WARP, AWG, Mesh, Olcrtc — 0644 и на месте).
- **Без глобального состояния модулей:** у каждой области своя структура, в тестах — подменяемые
  `runner` и корень файловой системы.

Зависимости: `google.golang.org/grpc`, `google.golang.org/protobuf`, `log/slog` (JSON в журнал),
остальное — стандартная библиотека. Netlink, nftables и D-Bus — вторым шагом, когда паритет
достигнут и проверен на узлах.

## 3. Поставка и обновление

- **Сборка:** статический бинарник (`CGO_ENABLED=0`) под amd64 и arm64, в CI на тег, вложением к
  релизу GitHub с файлом контрольных сумм.
- **SelfUpdate в Go:** скачать бинарник релиза, сверить SHA-256, проверить запуском `--version`,
  атомарно подменить, перезапустить юнит; прошлый бинарник остаётся рядом (`route-agent.prev`)
  для отката. Сеть нужна та же, что сейчас (GitHub), но без npm и сборки на узле. Позже можно
  доставлять бинарник от оркестратора тем же потоком, что sing-box (новый метод в proto — вместе
  с оркестратором).
- **`install.sh`:** скачивает бинарник, пишет тот же `.env`, юнит `ExecStart=/opt/route-agent/bin/route-agent`.

## 4. Переход узлов (самое опасное место, A §8.3)

Первый переход каждого стоящего узла выполняет **старый** агент своим зашитым SelfUpdate:
`git reset --hard @{u} && git clean -fd && npm ci && npm run build && systemctl restart route-agent`,
а юнит запускает `node dist/index.js`. Если в `main` окажется Go без `package.json` — узел уйдёт в
цикл перезапусков, и поднять его можно будет только по SSH.

Поэтому коммит слияния — **мост**:
- `package.json` остаётся, а `npm run build` запускает `scripts/bridge-to-go.sh`: скачивает бинарник
  релиза под архитектуру узла, сверяет сумму, переписывает юнит на бинарник, `daemon-reload`.
- Не скачалось или сумма не сошлась — `build` падает, цепочка останавливается до перезапуска, и
  работает старый агент (его `dist/` не трогается — `git clean -fd` не удаляет игнорируемое).
- Массовое обновление флота сейчас запускается только кнопкой (`recordFleetTarget`), поэтому
  слияние не раскатится само: узлы переходят по одному, когда их обновляют.

Порядок:
1. Тестовый узел ставится начисто или переводится `install-go.sh` из ветки с канала `preview`
   (пре-релиз `go-preview`); оркестратор гоняет на нём все действия журнала. Шаги — [`cutover.md`](cutover.md).
2. Один боевой узел переходит через мост (SelfUpdate), смотрим сутки.
3. Остальные — по одному или кнопкой массового обновления.

## 5. Тесты

- Каждая группа приносит тесты на Go по пунктам «Parity checklist» своей спецификации
  (в каждой — от трёх до пяти десятков пунктов), с подменой `runner` и файловой системы: проверяется, какие
  команды с какими аргументами и в каком порядке вызваны, какие файлы и с какими правами записаны.
- Интеграционный тест (замена `tests/app.test.ts`): сервер с тестовыми mTLS-сертификатами, все
  31 метод через настоящий gRPC-клиент, включая отказы авторизации.
- Тест хеша договора и формы версии.
- CI ветки: `go vet`, `go test -race`, сборка обеих архитектур; TS-проверки остаются до последнего коммита.

## 6. Найденное в нынешнем агенте

**Решения владельца (2026-11-06):** поведение переносится один в один, **явные ошибки и дыры
безопасности чинятся при переносе** и отмечаются здесь; хотфиксов в `main` не делаем — дыры 1–3
закрываются Go-агентом. П. 13 (смена, заметная оркестратору) владелец решил 2026-11-07: чинить.
Обновление Go-агента — бинарником из релиза GitHub (§3).

Отдельно — ошибка на стороне оркестратора, найденная при разборе: int64-поля трафика приходят
строками (`longs: String`), и свип складывает их как строки (`"500" + "600"`) —
`connectionsSweepService.ts:562`. Чинится в оркестраторе независимо от перевода.
